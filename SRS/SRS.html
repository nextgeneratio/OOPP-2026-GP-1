1. Introduction

1.1 Purpose

This SRS defines the functional, data, interface, quality, and object-oriented design requirements for a Java and MySQL desktop application that manages academic information for the Faculty of Technology. It is the baseline for analysis, design, implementation, testing, and demonstration in ICT2132.

1.2 Scope

The system manages role-based profiles, courses, materials, attendance, medical records, configurable assessments and marks, eligibility, grades, SGPA, CGPA, notices, timetables, and reports. It supports Admin, Lecturer, Technical Officer, and Undergraduate users. It is not an online student portal or a learning-management system.

1.3 Product Perspective

The product is a standalone, single-institution desktop information system using a Java GUI and a central MySQL database. It replaces fragmented spreadsheets and manual calculations with controlled data entry, consistent calculations, and read-only views appropriate to each role.

1.4 Definitions and Acronyms

TermMeaning
CAContinuous Assessment mark for an enrolled course; it is used for eligibility.
SGPA / CGPASemester / cumulative Grade Point Average, calculated as credit-weighted grade points.
Batch-missedA student who follows a course with a later or different batch because the original scheduled attempt was missed.

2. Overall Description

2.1 Product Perspective

The system has one source of truth for academic records. The GUI sends validated requests to controllers/services; services apply academic rules; DAOs use transactions to read and update MySQL records.

2.2 Product Functions

  • Authenticate users and show a dashboard based on their role.
  • Maintain profiles, courses, components, assessments, notices, and timetables.
  • Record theory/practical attendance and approved medical evidence.
  • Capture configurable assessments, calculate CA, eligibility, final marks, grades, SGPA, and CGPA.
  • Provide batch, course, and student reports without granting unapproved edit access.

2.3 User Classes

User classTypical knowledgePrimary responsibility
AdminTrained staff userMaster data, accounts, notices, timetables
LecturerAcademic staffMaterials, assessment marks, academic views

UndergraduateStudentOwn permitted profile and academic information

2.4 Operating Environment

Java SE 17+ desktop client (Swing or JavaFX), JDBC driver, MySQL 8+, Windows/Linux laboratory or office PCs, and a local/institutional network connection to MySQL.

2.5 Constraints

The application must use Java, MySQL, a GUI, and demonstrable OOP concepts. Every mark is out of 100. It must operate offline from the public Internet, except where the institution later chooses hosted database infrastructure.

2.6 Assumptions

Assumption A-01. The faculty supplies authorised course offerings, enrolments, timetable data, and final local approval for academic policies. This mini project implements those approved records; it does not replace Senate or examination-board decisions.

2.7 Dependencies

MySQL availability, JDBC configuration, Java runtime, accurate timetable setup, and authorised staff data entry are required for correct operation.

3. System Overview

Inputs

Profiles, course and component data, assessment definitions, marks, session attendance, medical details, notices, timetable entries.

Outputs

Role dashboards, attendance percentages, medical status, eligibility, grade/result views, SGPA/CGPA, and printed/exportable reports.

Calculation scope: Grade and GPA calculations use the grading scheme stated in Section 7. If a Faculty regulation differs from the published guidance, the administrator must configure the approved scheme and retain the approval reference; the system must not silently change historical results.

4. Functional Requirements

  1. FR-001 The system shall authenticate an active user by username and password and load only the functions assigned to the user role.
  2. FR-002 Admin shall create, read, update, deactivate, and maintain Admin, Lecturer, Technical Officer, and Undergraduate profiles.
  3. FR-003 Admin shall create and maintain departments, batches, courses, course offerings, components, notices, and timetables.
  4. FR-004 Lecturer and Technical Officer shall update their own profile except username and password; undergraduates shall update only contact details and profile picture.
  5. FR-005 Lecturer shall add and modify course materials for assigned course offerings.
  6. FR-006 The system shall allow configured assessment types per course offering, rather than assuming one common evaluation pattern.
  7. FR-007 Lecturer shall enter and revise marks out of 100 for authorised assessments and view them by student, batch, subject, and CA.
  8. FR-008 Technical Officer shall create and maintain timetable-linked theory and practical attendance sessions and records for current-semester modules.
  9. FR-009 The system shall show theory-only, practical-only, and combined attendance where both components exist.
  10. FR-010 Technical Officer shall create and maintain medical records; authorised users shall view their permitted medical records.
  11. FR-011 The system shall calculate attendance, CA, attendance eligibility, CA eligibility, and final examination eligibility.
  12. FR-012 The system shall calculate final marks, grades, grade points, SGPA, and CGPA and show supporting courses, credits, marks, and grades.
  13. FR-013 Users shall view notices and authorised timetable views; Technical Officers view only their department timetable.
  14. FR-014 The system shall produce the reports listed in Section 22 and keep an audit record of sensitive changes.

6. Detailed Module Requirements

6.1 Authentication & Authorisation

Purpose/actors: secure role-based access for all users. Pre/post: active account exists → authenticated session and role dashboard. Inputs: username, password. Processing/output: validate, compare password hash, log event, return dashboard or error. Validation/errors: blank/invalid credentials, locked/inactive account, unauthorised action.

6.2 User, Student, Lecturer & Technical Officer Management

Purpose/actors: Admin maintains role profiles; each role maintains permitted own fields. Pre/post: authorised actor → valid linked user/role profile is saved or deactivated. Inputs: identity, contact, department/batch/status details. Processing/output: check unique username/student ID, validate role scope, save profile; updated profile/list. Errors: duplicate identity, invalid email/phone, missing role link.

6.3 Course Management

Purpose/actors: Admin defines courses, offerings, credits, theory/practical components and enrolments. Pre/post: department exists → current-semester offering is available to authorised data entry. Inputs: code, title, credits, components, semester, batch. Processing/output: validate code/credits, prevent duplicate offering, save; course catalogue and offering view. Errors: invalid credit/component, duplicate course code, enrolment conflict.

6.4 Course Material Management

Purpose/actors: Lecturer publishes resources for assigned offerings. Pre/post: assignment exists → material metadata/path is available to enrolled students. Inputs: title, description, controlled file path/link. Processing/output: verify course ownership and file metadata; material list. Errors: unsupported file reference, missing title, unassigned lecturer.

6.5 Attendance Management

Purpose/actors: Technical Officer records timetable-linked current-semester attendance; lecturer/student read authorised views. Pre/post: offering, component, and timetable slot exist → one attendance record per student/session. Inputs: session date, component, enrolled students, presence. Processing/output: prevent duplicates, calculate counts/percentages; batch/student/component reports. Errors: session outside semester, absent enrolment, duplicate record, invalid component.

6.6 Medical Management

Purpose/actors: Technical Officer maintains submitted medical evidence and approval. Pre/post: student/enrolment exists → medical status is retained and used by eligibility rule. Inputs: student, course/period, date, reason, evidence reference, status. Processing/output: validate date/range, store pending/approved/rejected; medical view and eligibility input. Errors: future date, missing reason, overlapping duplicate record.

6.7 Assessment & Marks Management

Purpose/actors: Lecturer configures assessment components and records marks. Pre/post: lecturer assignment and offering exist → marks are saved against an assessment/enrolment. Inputs: assessment type/name, weight, CA flag, mark 0–100. Processing/output: validate total configured weights and mark range; mark, student, batch, subject, and CA views. Errors: duplicate assessment/mark, weight total invalid, unauthorised course, mark outside range.

6.8 Eligibility, Grade & SGPA/CGPA Management

Purpose/actors: system calculates academic outcomes; lecturer/student read authorised views. Pre/post: required attendance and marks exist → derived eligibility/result snapshot is displayed. Inputs: attendance records, medical approval, assessment marks, credits. Processing/output: apply Sections 7 and 16 rules; eligibility, grades, SGPA/CGPA with supporting courses. Errors: incomplete configured assessment, unavailable grade scheme, inconsistent credits.

6.9 Notice, Timetable, Reports, Profile & Dashboard

Purpose/actors: Admin publishes notices/timetables; all roles see scoped dashboards and reports. Pre/post: authorised record exists → targeted users receive readable current information. Inputs: title/body/audience/date or timetable slot/location. Processing/output: validate time collisions and audience; filtered views/reports. Errors: expired/blank notice, timetable overlap, invalid target audience.

7. Business Rules

IDRule
BR-001Only an active user with a verified password hash may create an authenticated session.
BR-002Role permission and data scope must be enforced for every create, read, update, delete, and report operation.
BR-003Each student may have one active enrolment per course offering; repeat/batch-missed attempts are separate enrolment records with an attempt number and status.
BR-004Every assessment belongs to one course offering, has a configurable type, and records marks from 0 to 100.
BR-005CA eligibility is true only when the calculated CA mark is at least 40.00%.
BR-006Attendance percentage for a component = (eligible attended sessions ÷ scheduled sessions) × 100. A theory/practical view uses only the matching component. Combined percentage = (eligible attended theory + practical sessions) ÷ (scheduled theory + practical sessions) × 100.
BR-007The standard scheduled count is 15 theory sessions and 15 practical sessions for a component offered in the current semester. A one-credit theory/practical component represents two contact hours per session; credits define course load, not a multiplier for the session percentage.
BR-008Assumption: attendance eligibility requires at least 80.00% in every required component. For a course with both components, the combined value is displayed, but eligibility requires each required component to meet 80% unless the Faculty formally approves a different policy.
BR-009Assumption: an approved medical record may convert eligible absence sessions within its approved date range into medical-excused sessions for the attendance calculation; those sessions are removed from the denominator, not counted as present. Rejected/pending medical records do not change attendance.
BR-010Final examination eligibility is true only if CA eligibility and attendance eligibility are both true. The system shall display the failed condition(s).
BR-011Final mark is the sum of each configured assessment mark × its configured weight / 100. Weights for a published assessment plan must total 100%.
BR-012The grade scheme and grade points follow the Technology-stream guidance of UGC Circular 12/2024 for applicable cohorts. The approved scheme is versioned so historic results remain reproducible.
BR-013SGPA = Σ(course credit × grade point) ÷ Σ(course credits counted in that semester). CGPA = Σ(course credit × grade point across counted completed attempts) ÷ Σ(counted course credits). Values display to two decimals.
BR-014Assumption: for a repeated course, the approved result-selection rule must be set by the Faculty; the mini-project default is to include the latest completed attempt in CGPA and retain all attempts for audit.
BR-015Passwords are never stored in plaintext. Profile image storage uses a controlled file path/UUID in the database; the GUI validates type and access location.

9. Object-Oriented Design Requirements

ConceptRequired use in this system
Classes & objectsDomain objects such as Course, Enrollment, Assessment, AttendanceSession, MedicalRecord, Notice, and Grade represent real academic concepts.
EncapsulationPrivate fields with validated getters/setters; for example, Marks.setScore() rejects values outside 0–100 and Assessment.setWeight() rejects invalid percentages.
Inheritance & abstractionAbstract User holds shared identity/authentication properties. Admin, Lecturer, TechnicalOfficer, and Undergraduate extend it and implement role-specific behaviour.
InterfacesRepository<T>, Authenticatable, and EligibilityPolicy reduce coupling and permit substitution in tests.
Polymorphism / overridingUser.getDashboardPermissions() and EligibilityPolicy.evaluate() are invoked through common types but execute role/policy-specific implementations.
Access modifiersPrivate data fields; protected shared user behaviour; public validated service APIs. DAO SQL helpers remain package-private/private where possible.
Exception handlingCustom ValidationException, AuthorizationException, NotFoundException, and DataAccessException are caught at controller boundaries and translated to safe GUI messages.
Database handlingDAO classes use JDBC prepared statements, result mapping, transactions, and try-with-resources; services must not build SQL in the GUI.
GUIViews collect input and render models only; controllers coordinate views and services so business rules remain reusable/testable.

10. System Architecture

10.1 Authentication, connection and transaction flow

  1. GUI submits credentials to AuthController; AuthService obtains the active user through UserDAO and compares a password hash.
  2. Service creates a role-aware session object and writes an audit event; no plaintext password is retained.
  3. DAO obtains a JDBC connection from a configured connection provider. Prepared statements prevent SQL injection.
  4. For an atomic operation (for example, publish assessment and marks), the service starts a transaction, calls DAOs, commits only after all steps succeed, otherwise rolls back.
  5. Input validation occurs in GUI for immediate feedback and again in service/domain objects for protection. Exceptions are logged and converted to user-safe messages.

16. Database Design

16.1 Design approach

The schema is normalised to practical third normal form: a person account is separated from role-specific data; student-to-offering, course-to-lecturer, and assessment-to-mark relationships use junction/child tables; derived GPA is calculated from results rather than duplicated as a permanent source of truth. Profile pictures use a controlled relative file path/UUID rather than BLOB to keep routine database backups and queries lightweight.

21. GUI Requirements

All screens shall have a clear title, logged-in role/name, navigation, validation messages near inputs, confirmation before destructive/locking actions, and only role-authorised controls.

1. Login

Username/password fields, Login button, error label; all roles; validates active credentials.

2–5. Role Dashboards

Admin, Lecturer, Technical Officer, Undergraduate shortcuts, scoped alerts and summary counts; read-only summary data.

6. User Management

Admin: role selector, profile form, search table, Create/Update/Deactivate buttons; validates unique account identity.

7. Student Management

Admin: student/batch/contact/status fields and listing; validates student ID, batch and role link.

8. Course Management

Admin: course/offering/component/credit fields, assignment and enrolment tables; validates codes, credits, duplicates.

9. Attendance

Technical Officer: timetable session selector, component filter, presence grid, Save; lecturer/student view only by scope.

10. Medical Management

Technical Officer: student/course/date/reason/evidence/status controls; approval list and validation messages.

11. Marks Entry

Lecturer: offering/assessment/batch selectors, marks table, Save/Update; requires 0–100 and course assignment.

12. Eligibility

Lecturer: student/batch/course filters, attendance/CA/final status and reasons; student sees own status.

13–14. Grade / GPA Screens

Lecturer and student: courses, credits, final marks, grades, grade points, SGPA/CGPA; no manual edits.

15. Timetable

Admin editor; other role-specific read views; day/time/location grid with conflict validation.

16. Notice

Admin compose/publish/expire controls; all roles read targeted notices.

17. Course Materials

Lecturer add/edit/delete authorised materials; enrolled students view list.

18. Profile

Own profile fields; username/password locked; undergraduate contact/picture-only edit.

19. Reports

Authorised filters, preview table, print/export action; no raw data outside scope.

24. Assumptions and Limitations

24.1 Assumptions

CategoryAssumption
AcademicFaculty supplies final approved course offerings, enrollment selection, assessment weights and any programme-specific policy exception.
TechnicalAll client computers can run the selected Java GUI runtime and reach the authorised MySQL server.
DatabaseProfile image files are stored in an access-controlled application directory and database stores only controlled paths/UUIDs.
Attendance15 sessions are planned for each theory/practical component; approved medical absences are removed from the denominator (BR-009).
GradingUGC Circular 12/2024 scheme applies to the relevant Technology-stream cohort; Faculty must confirm any local exception and repeat-result selection rule.
SecurityAdmin provisions initial accounts securely; password reset procedure is a controlled institutional process outside this mini-project scope.

24.2 Limitations

  • Desktop application for a single institutional deployment; no mobile app or public Internet-facing portal.
  • MySQL availability and local network connectivity are required for shared live data.
  • Medical evidence is represented as validated details/reference; a public online upload portal is not included.
  • The system calculates from approved configured data but does not replace formal examination-board approval.

25. Future Enhancements

  • Web and mobile applications with secure single sign-on.
  • Email and SMS notifications for notices, eligibility and timetable changes.
  • Parent portal, online medical upload workflow, and document scanning.
  • Advanced analytics for attendance/assessment trends and risk indicators.
  • Cloud deployment, automated backups, and University LMS integration.

These items are explicitly future enhancements, not current functional requirements.

26. Conclusion

This SRS defines a feasible Java + MySQL GUI mini-project with scope-controlled roles, configurable academic assessment, correct theory/practical attendance treatment, medical approval, eligibility, grades, SGPA/CGPA, and an OOP-oriented layered design. The explicit assumptions protect the project from presenting unconfirmed local academic policies as official rules.
